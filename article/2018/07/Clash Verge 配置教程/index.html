完整的请求处理流程

先匹配规则（Rules），在必要时才触发域名解析（DNS / Nameserver）。

当一个带域名的请求进入 Clash 时，处理顺序为：

  1. 扫描 Rules 规则列表

    Clash 不会一收到域名就立刻跑去请求 DNS 解析，而是先拿原始域名去逐行匹配 rules。

  2. 匹配到 域名规则 时，直接决定去向（无需 DNS）

    如果匹配到了 DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD 或 GEOSITE：

    • 走 Proxy（代理）：将域名直接发送给远端代理节点，由代理节点去解析 IP 并连接，本地完全不触发 DNS 解析。

    • 走 DIRECT（直连）：调用 nameserver 解析 IP，然后直连。

  3. 匹配到 IP 规则 时，按需触发域名解析

    如果前面的域名规则都没命中，扫到了 IP-CIDR 或 GEOIP 规则：

    • 未带 no-resolve：Clash 会暂停规则匹配，调用 nameserver 将域名解析为 IP，然后再拿这个 IP 去比对是否符合该 IP 段。

    • 带了 no-resolve：Clash 跳过这条规则，不进行 DNS 解析，继续往下匹配后续规则。

  4. 兜底规则（如 MATCH,Proxy）

    如果一路扫到底都没有命中任何直连规则，最终走到了 MATCH,Proxy（全局代理）：

    • 域名同样会直接交给代理服务器，本地不会向 nameserver 发起解析请求。

配置优先级

Clash Verge 在处理流量时，各类扩展脚本和配置的加载优先级如下：

  1. 全局扩展配置（最高优先级）
  2. 全局扩展脚本
  3. 订阅扩展配置
  4. 订阅扩展脚本（最低优先级）

提示：全局扩展配置 和 全局扩展脚本 会作用于所有订阅 Profile，适合放置公司内网分流、本地 DNS 覆盖等通用固定需求。

全局扩展覆写配置（YAML）

dns.nameserver-policy

作用： DNS 服务器。该配置支持 geosite 语法，且优先级高于普通的 nameserver 与 fallback 查询。

应用场景： 强制让国内常见域名和公司内网域名使用 **系统默认 DNS（system）**进行解析，防止内网域名被发送至远程 DNS 导致解析失败或泄露。

前置路由规则覆写

作用： Clash 的路由规则将按照从上到下的顺序匹配，列表顶部的规则优先级高于其底下的规则。通过 JavaScript 脚本将自定义规则动态插入到规则列表的最上方，可确保关键请求直接命中，不触发后续订阅自带的规则。

应用场景： 防止通用的地理位置规则（如 GEOIP,CN）或兜底规则（如 MATCH,Proxy）误拦截内网流量，导致内网或本地 IP 段误走代理。
