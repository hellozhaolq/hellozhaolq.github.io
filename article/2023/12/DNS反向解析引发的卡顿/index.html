DNS反向解析引发的卡顿

发表于 2023-12-07 分类于 其他

推荐链接：

反向 DNS 解析（Reverse DNS lookup）：从 IP 地址查询域名/主机名 的网络行为（与传统的 从域名查 IP 相反）。

PTR（Pointer Record，指针记录）：DNS 系统中专门用来实现反向解析的一种数据记录类型。就像正向解析用 A 记录（域名 → IPv4）或 AAAA 记录（域名 → IPv6）一样，反向解析在 DNS 数据库里用的就是 PTR 记录（IP → 域名）。

DNS 反向解析是一个动作，而 PTR 记录是完成这个动作所依赖的数据文件。

为什么很多服务默认要进行反向解析？

明明已经拿到了客户端 IP，为什么还要查域名？原因是部分服务并不仅仅关心 IP，而希望知道：“这个连接来自哪台机器？”。常见原因如下：

  • 安全与权限控制：MySQL 支持基于主机名授权 GRANT SELECT ON db.* TO 'root'@'host-a.local';，所以它需要把客户端 IP 解析成主机名。
  • 安全审计和日志记录：在日志中记录 hostname 比记录一串无意义的 IP 更直观。
  • SASL / Kerberos 身份认证：一些安全认证体系会依赖 hostname，用于确认客户端的真实身份，防止中间人攻击。
  • IP 经常变化，基于主机名的授权更便于管理。

反向解析导致卡顿的通用流程

为什么 DNS 反向解析 失败/超时 后还能继续后续流程？

DNS 反向解析失败 ≠ 客户端连接失败。

以 MySQL 为例：

DNS 反向解析超时不会直接拒绝连接，因为它通常只是为了获取 hostname 的辅助步骤；超时后服务会降级使用 IP。只有当 权限控制 或 认证协议 强依赖 hostname 时，才会导致连接失败。

如何测试是否存在反向解析问题？

反向解析问题和解决方案

对于由“反向解析超时”引发的卡顿，解决思路非常一致：要么补齐 PTR 映射（改 hosts），要么直接关闭服务的反向解析功能。

应用场景 现象 根因 最佳解决方案
MySQL + Navicat Navicat 点击连接后，要停顿 3~5 秒甚至更久才能连上，但连上后操作又很顺畅。 MySQL 默认开启主机名解析（skip_name_resolve=OFF），根据客户端 IP 查询 PTR 记录超时。 关闭反向解析（推荐）：skip_name_resolve=ON
Kafka / SASL Java 客户端 或 Kafka命令行工具 连接慢 SASL 安全库（如 GSSAPI/JAAS）在握手阶段对 Broker IP 进行 PTR 反向域名查询。 修改本地 /etc/hosts（推荐）： 添加 192.168.0.7 hostname-01 映射，让系统直接本地返回，跳过外网 DNS 超时。
Linux SSH ssh user@ip 执行后，输入密码前，卡顿几秒。 SSH 服务端（sshd）开启了 UseDNS yes。
查询默认值：`sshd -T		 grep -i UseDNS`。
